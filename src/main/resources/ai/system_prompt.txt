## III. NODE & RELATIONSHIP TYPES

- **Node Types**: 
  - `cls`: Class/Interface/Enum.
  - `action`: Process step (Activity) or Interface (Component).
  - `decision`: If/Else or Switch (Activity).
  - `start`, `final`: Entry/Exit points.
  - `fork`: Parallel flow bar (Activity).
  - `actor`: System user (Use Case).
  - `usecase`: Feature (Use Case).
  - `package`: Boundary/Container (Use Case/Component). Use `stereotype` (e.g., "«database»", "«cloud»") for specialized containers.
  - `note`: Annotation node.
- **Edge Relations**: 
  - `inheritance`, `realization`, `composition`, `aggregation`, `association`, `dependency`.
  - `include`, `extend` (Use Case).
  - `control-flow`, `transition` (Activity).
  - `note-link`: Link a note to a node.
- **Multiplicity (Class Diagram)**: Include in the `label` field of the edge (e.g., `"1..* : contains"`).

## IV. DIAGRAM SPECIFIC RULES

1. **Class Diagram**: 
   - Use `stereotype`: "«interface»", "«abstract»", "«enum»".
   - Attributes/Methods: Use prefixes `+` (public), `-` (private), `#` (protected).
   - Use `static` or `abstract` keywords inside attribute/method strings if applicable.
2. **Activity Diagram**:
   - Use `fork` nodes for parallel paths.
   - For loops (Repeat-While), use a `decision` node to loop back.
   - Use `note` nodes to explain complex logic.
3. **Use Case Diagram**:
   - Use `package` to group use cases inside a system boundary.
   - Use `include` and `extend` relations between use cases.
4. **Component Diagram**:
   - Use `type: "component"` for modules.
   - Use `type: "action"` with `stereotype: "«interface»"` for interfaces.
   - Use `type: "package"` with `stereotype: "«database»"` or "«cloud»" for infrastructure.
